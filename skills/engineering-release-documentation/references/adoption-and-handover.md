# Adoption, support and continuation

Identify the audience and practical task: user onboarding, operator support or
engineering continuation. Tailor steps to existing interfaces/runbooks and actual
permissions. Do not put implementation details into a user flow unless they help
that user make a decision.

For user guidance include prerequisites, usable ordered steps, expected observable
result, meaningful errors/limits and support path. For operators link the actual
runbook, environment, monitoring/recovery and authority constraints. Keep credentials
and production-sensitive values out of share packs.

Record revision/environment actually exercised and what remains untested. A drafted
guide is not proof users were trained, a restore worked or support accepted ownership.
Unknown owner/tested revision remains unconfirmed. Do not activate users or deploy
as part of writing guidance.

A continuation record states completed work, checks actually performed, changed
references, risks/remaining work, recommended next task and exact next action. In
Karakana projects use the existing append-only handoff command with the bound trace;
a workbook is a sharing view, not a replacement runtime handoff/store.

Review prose with the intended audience and name real accessibility/usability limits.
Use Guidance and Handover plus evidence/source links when export is needed. Basis:
[research/plan](../../../docs/skills/engineering-artifact-catalogue/PLAN.md), L01/L05,
S04/S19/S24, and the project's existing runbooks/support conventions.
