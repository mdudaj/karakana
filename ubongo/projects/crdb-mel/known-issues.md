# Sustainable Finance MEL Platform Known Issues

- Product identity has been revised from TACATDP to Sustainable Finance MEL Platform. Do not blindly rename existing `TACATDP_*` Power Platform artifacts because deployed schemas, lists, controls, and source-form terminology may still depend on those names. Use Sustainable Finance MEL Platform for documentation/product identity and TACATDP for historical/programme/deployed artifact context.

- Dataverse privileges are not available, so Dataverse-first solution deployment is blocked for now.
- Power Apps Git integration does not create Microsoft Lists or fully deploy a new app from scratch.
- Large reference lists can produce incorrect results if Power Fx formulas are nondelegable.
- Long XLSForm-style surveys can become unusable if generated as one giant dense form.
- SharePoint required columns conflict with skip logic when hidden fields are still required by the data source.
- Configuration Migration Tool schemas use lowercase Dataverse logical names and encode lookup fields as `type="entityreference"` with `lookupType` set to the referenced table logical name. Using the generic `type="lookup"` causes target validation to report valid lookup columns as missing. CMT 9.1.0.365 still rejected the valid `mp_formattachment.mp_file` column when encoded as `filedata`; use the governed Package Deployer release with Dataverse block file messages for the TACATDP seed and XForm instead of patching CMT archives.
- CRDB Power Pages onboarding can create Contact, Invitation, and `mp_formassignment` rows without completing Microsoft identity activation. On 2026-07-31, CRDB checks showed Denis and Hailo had `adx_externalidentity` rows and could access the portal, while affected non-admin invitees had active assignments and active `New` invitations but no external identity rows; `adx_inviteredemption` returned no records. Treat users as `Pending activation` until the invitation is redeemed, the invitation leaves `New`, and an `adx_externalidentity` exists. Do not diagnose this as an app assignment/email-pattern issue until contact uniqueness, invitation status, invite redemption, external identity, web role, and assignment are checked together.
- Private Power Pages site visibility is a separate access gate before TACATDP web roles, table permissions, invitations, and assignments. In Mshirika and CRDB developer/non-production sites, non-admin testers must be added under Power Pages Studio > Security > Site visibility > Grant site access before invitation redemption/sign-in can complete. If the public/private radio controls are disabled, do not diagnose TACATDP code first: Microsoft tenant governance or developer-site restrictions may be forcing the site to remain private. The correct private-site test checklist is: grant site access for the CRDB Entra user, then redeem invitation, then verify `adx_externalidentity`, web role, and active assignment.
- The Power Pages ODK runtime must not rely only on the third-party `loaded` event to remove a blocking form loader. On 2026-07-31, CRDB showed the runner stuck at "Preparing the form runtime" while the form appeared blurred behind the overlay. Keep a timed mount fallback that clears the overlay after the ODK host mounts, and show an actionable status instead of trapping the user behind a full-screen spinner.
- Power Pages site exports can include secret-bearing `sitesetting.yml` values. On 2026-08-02, GitHub push protection blocked TACATDP branch push because the CRDB deployment artifact included an Azure AD application secret in `artifacts/deployments/.../tacatdp-monitoring-tool/sitesetting.yml`. Do not commit raw Power Pages `sitesetting.yml` exports from live environments. Scrub or omit sensitive site settings before packaging documentation artifacts, and verify with secret scanning before push.
- Power Pages SPA asset renames can leave users on stale shell code even after portal cache purge and site restart. On 2026-08-03, Mshirika still showed the old shell because localized Home content and old JS/CSS web-file names were not updated together. For shell releases, verify both the main Home page and localized Home copy reference the current asset marker, and overwrite previous JS/CSS asset filenames as compatibility aliases until old cached HTML can no longer be served. Confirm by downloading the live site with PAC and scanning the returned Home pages plus old asset filenames for stale route markers and forbidden shell controls.
- CRDB PAC access with Denis can upload Power Pages and read Dataverse records using `pac env fetch`, but it is not a general Dataverse PATCH channel. Do not route CRDB one-row fixes through Azure CLI when Denis lacks Azure tenant permission. For record writes use one of: approved service principal/Azure token, model-driven/Maker table UI, Power Pages Web API from an authorised admin session, or a packaged server-side processor.
- Project/form visibility requires both the correct Power Pages web role and an active TACATDP assignment row. On 2026-08-04, CRDB showed Denis and Hailo both linked to the same `Platform Administrator` web role, but Hailo's `mp_formassignment` row did not return `mp_lifecyclestatus=Active`; the SPA filters assigned forms by `mp_lifecyclestatus eq 100000000`, so Hailo can have the right portal role and still see zero projects. Before cache purge/restart, compare contacts, web-role links, external identities, and active assignment lifecycle values against a known-working user.
- Admin User & Access lists must not be built from active assignments only. On 2026-08-04, Hailo still had an active Contact and stale `mp_formassignment` row, but disappeared from the UI list because `listAllFormAssignments()` filtered to active lifecycle rows. Admin access-management screens should include inactive/stale assignment rows, mark them `Needs admin review`, and allow the assign/reactivate workflow to repair them.
- User & Access role labels and resend metadata must come from actual Contact-to-Power Pages web-role links, not from the current signed-in user's session roles. On 2026-08-04, Hailo had the real `Platform Administrator` web role, but the UI classified every non-current user as `Data Collector / Bank Officer`; resending an invitation copied that incorrect UI label into `mp_targetrole`. Fix role derivation by querying each Contact's linked web roles and only use the current-session fallback for the signed-in user when role lookup is unavailable.
- PAC authentication against Mshirika can fail with "You don't have access to this resource" even when the tenant user is visibly signed in to Maker Portal for the correct `PowerPagesDeveloper-*` environment. Do not conclude that `john.mduda@mshirikacorp.onmicrosoft.com` lacks Mshirika access from the org URL auth failure alone. If Maker shows the environment, extract the environment id from the Maker URL, for example `07b77aa3-c0c0-e513-8b8c-407b83639a45`, and retry `pac auth create --deviceCode --environment <environment-id>` plus `pac pages list --environment <environment-id>`. Use the work/school tenant account, not the personal Hotmail account, when completing the device-code prompt.
- For Mshirika on this Linux/PAC 2.10.1 setup, do not introduce Azure CLI as the default fix. Historical Mshirika/CRDB work used ordinary PAC user auth to Power Platform. `pac auth create --managedIdentity --environment 07b77aa3-c0c0-e513-8b8c-407b83639a45` followed Microsoft guidance for Azure Identity/VS Code-style credentials but failed with `Azure.Identity.CredentialUnavailableException`; the diagnostic said `VisualStudioCodeCredential requires the Azure.Identity.Broker package`, Azure CLI was not installed, Azure Developer CLI was not found, and the Visual Studio token provider path was unavailable. Treat that only as evidence that VS Code/Azure Identity reuse is unavailable in this shell. First retry normal PAC browser auth with `pac auth create --environment <environment-id>` using the Mshirika work/school tenant account.
- CRDB PAC deployment access has used device-code login with the `dmuroba@crdb.co.tz` / Denis Muroba user profile. That profile is the expected human delegated PAC deployment profile for CRDB, not the project service principal or CI principal. Do not infer service-principal privileges, app-user configuration, CI credentials, or production principal ownership from successful CRDB PAC commands run through `dmuroba@crdb.co.tz`.
