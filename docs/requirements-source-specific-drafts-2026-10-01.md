## Task classification, requirements note, and source evidence

This is a bounded Python behavior change to Karakana's deterministic requirements generator. The project backlog's KDX-08 asks for concrete source requirements and criteria to appear in reviewable story and issue drafts without invented actors, outcomes, or approval. KDX-06 already rejects fallback PRDs at readiness, but `karakana/requirements/stories.py` still generates five fixed requirements-harness slices for every non-MSc project. `karakana/requirements/issues.py` repeats those slices and all PRD requirements in each issue. `karakana/requirements/summary.py` describes each actor as wanting “the capability described by this PRD.” Current tests assert the fixed five-slice behavior. These source files, the KDX-06 delivery record, the project backlog, and the engineering-requirements story guidance govern this change.

## Design, look and feel, traceability, and artifact readiness

Keep the existing `RequirementPRD`, `UserStory`, and `IssueDraft` schemas and stable derived IDs. Reuse KDX-06 source-grounding metadata and known fallback strings to distinguish explicit content from generated defaults, including legacy PRDs without metadata. Add a separate `actors_grounded` boolean and parse explicit `Users / Actors:` bullets or `Actor:` text; remove the PRD's heuristic actor defaults so its JSON and Markdown do not imply source evidence that does not exist. Each explicit functional requirement becomes a draft; one requirement can directly use the source criteria, while multiple requirements repeat them with an explicit mapping-review label. A fallback PRD yields one provisional draft and no invented implementation scope. Issues carry only their corresponding story's source requirement, criteria, and review caveats.

The output is technical Markdown, not a graphical interface. Retain existing headings and simple bullets. Show actor, requested behavior, and outcome as labeled fields so missing values read naturally. Use direct “Needs review” copy for missing evidence and make the next action clear. This follows `skills/ux-writing/SKILL.md` and the existing renderer style. When `requirements issues` finds the exact prior five-story template, regenerate those stories from the PRD and report that action. If it finds that template with edits, stop before creating issues and give the explicit regeneration command; preserve the edited stories for human review. There is no design-system, accessibility, storage-schema, database, authentication, permission, deployment, or external API change. A criterion copied into several drafts is explicitly an unconfirmed mapping, not an acceptance claim. The generator cannot infer semantic links or reviewer approval.

The backlog item and this record supply the requirement and PRD; D1–D5 are its acceptance criteria and traceability. The user story is above. The design and behavior examples here serve as the artifact-readiness decision. A separate ADR, UX mockup, schema change, migration, and release artifact are not applicable. This task is ready for local implementation under the existing instruction; publishing remains a separate authority decision.

## Change and verification summary

The non-MSc generator now produces one story and issue per labeled source requirement and one provisional draft for a generic fallback. Source criteria appear verbatim for a single requirement, or with an explicit mapping-review label when several requirements share an unmapped criterion list. Explicit actors are parsed from `Users / Actors:` or `Actor:`; otherwise the actor and any ungrounded outcome are marked for review. The PRD renderer no longer shows invented actor defaults or the vague “capability described by this PRD” story. The exact old five-story template is regenerated before issue creation; an edited copy is preserved and issue creation stops with a recovery command. The MSc-specific story and issue generators remain unchanged.
