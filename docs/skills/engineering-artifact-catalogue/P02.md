## Artifact readiness and scope

As a document author, I want a source-validated sharing view and a feedback report
so that each audience can review the same baseline without creating another master.
As a reviewer, I want changed, stale and conflicting input reported by source
identity so that agreement in a workbook cannot silently alter source approval.

Implement one opt-in module CLI/API in `karakana/tools/engineering_artifacts.py`,
its isolated tests, documentation and optional `workbooks` dependency. Preserve
engine schemas/store/readiness and global blank assets. No source/approval writes,
live models, remote publishing, migration, deployment, skills/index/skillpack
installation or real project release drafts are included.

| Condition | Observable check / test coverage |
| --- | --- |
| A01: strict authored Markdown metadata/headers, unique qualified IDs and explicit namespace | Duplicate keys/IDs, unsupported version, missing namespace and malformed tables reject |
| A02: read-only native adapters and persisted binding identity | Native PRD/story/issue IDs, strict models, file/text hashes, duplicate/reordered/changed strings and source drift; original bytes unchanged |
| A03: new binding/reconciliation proposals, never automatic registry approval | Persist stable IDs in a new Markdown proposal; ambiguity remains unresolved; existing IDs reused only with declared association |
| A04: five explicit audience profiles and complete source manifests | Relevant content selected; native identities/full-source links/hashes retained; omitted detail declared; blockers survive |
| A05: workbook and snapshot form an immutable comparable baseline | Exact snapshot/workbook parity, payload/source hashes, root/overwrite/alias guards and tamper rejection |
| A06: three-way returned-workbook feedback | Field edits, added/deleted rows, altered identities, stale sources, same-field conflicts, conflicting workbooks, formulas and unknown sheets reported; all inputs unchanged |
| A07: structural claims and review/test evidence separated | Missing pass/approval evidence rejects; native recorded status retained with limits; feedback never mutates approvals |
| A08: safe workbook transport | Literal leading formula-like strings, no macros/external calculations, readable tables/frozen identities, supported office round trip |

Definition of Done: focused regression cases and required broader suite pass,
actual CLI exports/feedback and rendered samples work; review the diff, document
supported limits and append a bound handoff. Structural checks are not substantive
approval or proof that author-provided observations actually happened.

## Usage

Install the optional workbook dependency when exports/feedback are needed:

```bash
python -m pip install -e '.[workbooks]'
```

The `dev` extra also includes openpyxl so existing CI test installation exercises
the workbook regressions. Markdown validation and binding proposals use the base
dependencies. Invoke the
module explicitly; it is not automatically run by existing Karakana commands.
Paths are relative to `--root`, which defaults to the current directory; linked
source paths in Markdown are relative to that document. All resolved sources
and outputs must stay within the root. Known credential paths are refused.

Instantiate a copy of the generic template, keep applicable exact table headers
and explicit anchors, and add the scalar frontmatter required by the contract.
The blank template itself is not an instantiated export source. Use explicit
stable namespaces; do not infer one from a project/repository name.

```bash
python -m karakana.tools.engineering_artifacts --root . validate \
  --source source.md --namespace example

python -m karakana.tools.engineering_artifacts --root . export \
  --source source.md --namespace example --audience business \
  --baseline-revision reviewed-source-revision \
  --output review/business-v1.xlsx --snapshot review/business-v1.json

python -m karakana.tools.engineering_artifacts --root . bindings \
  --source native-source.json --namespace example \
  --registry source.md --output review/new-binding-proposal.md

python -m karakana.tools.engineering_artifacts --root . feedback \
  --baseline review/business-v1.xlsx --snapshot review/business-v1.json \
  --returned review/business-v1-annotated.xlsx \
  --output review/feedback-v1.json
```

Create the output directory first. Repeat `--source` for related documents and
`--returned` for independent reviewers. Omit `--registry` for a new binding
proposal. Proposal output retains existing IDs where the association is known;
new/reconciled mappings require review and explicit persistence in canonical
Markdown before export. No command applies feedback or resolves approvals.

Profiles are `business`, `engineering`, `qa`, `operations` and `executive`.
Every profile includes source hashes, declared revisions (or `not recorded`),
document states, test/release limitations and risks. Detailed omitted tables and
full narrative source links are declared; engineering also includes narrative.
The baseline revision is caller-supplied, not proof of a clean Git tree. Engine
status/readiness is labelled as a recorded source result rather than approval.
Source-manifest kinds/authorities supported here are exactly `Authored Markdown`,
`Engine JSON` and `Machine source`; unknown/conflicting authority blocks export.

Archive the original XLSX and JSON snapshot unchanged. Share a copy with source
documents if relative source hyperlinks must work for recipients. Reviewers can
use yellow `Feedback` cells, comments or proposed value/row edits. Keep row-4
headers and the first three identity columns intact; row sorting is supported.
Changed identities appear as removed/added rows. The report compares the original
baseline, current sources and returned workbook, and flags stale files, invalid
current sources, row/field conflicts, formulas and unsupported worksheet changes.
Review proposed changes through the governing source workflow, then export to
new filenames. Workbooks and reports never establish reviewer authentication.

The Python API exposes `load_bundle`, `propose_bindings`, `export_workbook` and
`feedback_report`; it has the same read-only/source and new-output boundaries.
CLI exit codes are 0 for successful validation/output and 2 for a refused input
or output. Feedback with conflicts is a successful report, not an approval.

## Supported limits and verification

This is a narrow table/frontmatter convention, not a general Markdown parser or
spreadsheet editor. Source files and baseline JSON inputs are limited to 2 MB; supported XLSX transport is
20 MB compressed, 64 MB expanded and 2,000 ZIP entries. Cells retain literal text
up to Excel's 32,767-character limit; oversized/control-character values reject.
Export also refuses a workbook/snapshot exceeding its later input limits; split
the source set instead of creating an unusable comparison baseline.
Macros and external calculation links reject without changing the input. Formulas
in returned cells are reported as proposed input and never evaluated. Unsupported
formatting, charts, validations or drawing edits are not semantic feedback;
the original annotated workbook remains the evidence.

Exports use named tables, wrapped Arial text, frozen identity columns, source
links, labelled feedback cells and repeating print headers/identity columns. Wide
tables print across two A3 landscape pages; long narrative rows may require
opening the cell/source to inspect the whole retained value. Export is not an
accessible PDF publishing system. Native Excel and assistive-technology checks
are unperformed; LibreOffice compatibility is local evidence only.
